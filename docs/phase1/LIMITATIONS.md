# Jury Q&A: Limitations and Honest Scope

1. **What is Prahari?** An offline, advisory on-device threat-triage assistant for Indian SMS/WhatsApp-style messages, phishing URLs, QR payloads, and network events. It helps a user decide what to verify next; it does not block communications or act automatically.
2. **Does it run Llama through ExecuTorch on physical Arm hardware?** Yes. On a physical **Samsung Galaxy S23 (`SM-S911B`, Snapdragon 8 Gen 2, `arm64-v8a`, Android 14)** via Samsung Remote Test Lab, Prahari ran the verified `Llama-3.2-1B-Instruct-QLORA_INT4_EO8.pte` via ExecuTorch Android 1.5.1 XNNPACK at **43.4 tok/s warm** (**510 ms TTFT**, **1.20 s/check**) and **39.0 tok/s / 1.42 s in Airplane Mode**. Separately, Arm Linux was verified on **Arm Neoverse-V2** (46.7 tok/s at 2T, 104.6 tok/s at 8T) and an Oracle **Neoverse-N1** VM (19.9 tok/s).
3. **What is the current Android APK status?** The physical S23 measurements ran the r1 `arm64-v8a` APK. Round-2 features merged in PR #43 (Share sheet, `EN / Hindi` UI toggle, offline `Listen` TTS, quoted evidence spans, opt-in redacted history, pure-Python QR decoder) and PR #41 explanation-honesty fixes were verified in CI and on an Android 14 x86_64 emulator. Round 3 (PR #45, merged 24 Nov: Hindi-only chrome, share preview, amber bank-alert banner, large-font layout, TalkBack labels, memory hygiene) was also checked only on the emulator. The final APK has not yet run on a physical phone; the S23 re-run is required before recording the demo video.
4. **Is it truly offline?** Yes at inference time. The Android APK declares **no `INTERNET` permission** (verified by CI `aapt` check and live `SecurityException` in 12 ms on S23) and completed inference on the S23 with **Airplane Mode ON (`airplane_mode_on=1`)**. On Arm Neoverse-V2 Linux, inference succeeded 6/6 inside an isolated `unshare -n` network namespace where HTTPS, DNS, and raw TCP all failed. One-time package install and model staging require a network-capable machine, and tapping `Call 1930` or `Report on Chakshu` opens separate system apps.
5. **Does it monitor live network traffic?** On Linux, `candidates/BEST/bin/monitor` (PR #40) samples `/proc/net/tcp`, `/proc/net/tcp6`, and `/proc/net/snmp` every 0.5 s with no root and no packet capture to detect port scans, login-port repeats, half-open floods, periodic connections, and failed-connect/reset bursts. It is Linux-only (Android 10+ restricts `/proc/net`), misses connections shorter than the 0.5 s sampling interval except via address-less kernel counter jumps, and does not capture raw packet payloads.
6. **How does the NSL-KDD flow model relate to `bin/monitor` and `bin/explain`?** They are separate paths. `bin/predict --task flow` runs a trained HistGradientBoosting model + 3 signatures over NSL-KDD's 41 named features as dataset replay (F1 0.850, FPR 3.03% on `KDDTest+`). `bin/monitor`, the web UI, and `bin/explain` classify plain-text network descriptions using flow text rules, so the two paths can disagree and `bin/explain` does not explain the tree model's verdict.
7. **Why do the two holdouts differ (v3 held-back F1 0.970 vs. sealed 0.813)?** After PR #48 the v3 held-back split (`n = 81`) has no false alarms (FPR 0.000, recall 0.941) and the new blind 240-message validation set has FPR 0.120 at recall 1.000, but the v4 held-back split (79 messages the fixing thread never saw) still has FPR 0.277 (was 0.340), and the older Gemini-authored sealed holdout (`n = 184`, scored at several checkpoints) still flags 28 of 87 genuine SMS (SMS FPR 0.322, combined FPR 0.300, recall 0.929). Every link in that holdout uses the `.example` placeholder, which the contact gate treats as a contact and the domain rules call risky; the rest of its false alarms are chats warning relatives about scams and doorstep/self-check notices. The v3 split was also used as a check during PR #48, so it is no longer untouched.
8. **Does Prahari routinely flag legitimate bank or OTP SMS?** Genuine-looking bank debit and OTP alerts without an unofficial contact are shown with an amber **CHECK THIS ALERT** banner rather than `DANGEROUS` (raised to SUSPICIOUS if the alert carries an unofficial link or private number), guiding the user to verify directly in their bank app. PR #48 cut false alarms on genuine messages (fp_val_v1 FPR 0.207 -> 0.120, sealed SMS FPR 0.402 -> 0.322), but advisories with their own link and scam-warning chats are still flagged too often — which is why background `READ_SMS` interception is intentionally off.
9. **How fast and memory-heavy is it on a real phone?** On Galaxy S23 (8 GB RAM), warm text checks take **1.20–1.50 s** (1.42 s in Airplane Mode; the lookalike-URL check took 3.53 s), but `dumpsys meminfo` recorded **1.66 GiB PSS / 1.78 GiB RSS** (89.8% Native Heap). App-displayed memory went from 1,692 MB to a 1,781 MB peak across 8 checks (1,773 MB at the end). On the emulator the final build held steady over 10 checks (−4,885 KiB from check 2 to check 10, PR #55), but no long session has been measured on a phone. Shrinking KV-cache context length and freeing per-check native buffers is needed for comfortable headroom on 4–6 GB phones.
10. **What does Arm KleidiAI actually contribute?** Whole-process `perf record -F 99 -g` profiling on Arm Neoverse-V2 (2 threads, 2,222 samples, 0 lost) proved **54.17% of sampled CPU time** executes directly inside named `kai_*` kernels (`23.27%` `i8mm` prefill matmul + `20.57%` `dotprod` decode matmul + `10.33%` packing/helpers) invoked through ExecuTorch's XNNPACK delegate. No runtime KleidiAI disable flag was found in the installed ExecuTorch build, so dispatch is proven without claiming an unmeasured on/off speedup ratio.
11. **Are Llama explanations always reliable?** No. An initial blind audit of 20 sealed-holdout explanations found 5 correct, 8 weak, and 7 wrong (4 false input claims). PR #41 fixed repeated openings, false absence assertions on `NO RISK` items, and stray generated questions (lifting automated consistency v2 from 0.929 to 0.964 and explanation score from 0.929 to 0.932), and vetted static steps are always displayed first PR #50 then grounded the second sentence in a vetted fact and drops sentences that claim things the message lacks, but its three blind audits (20 fresh items each, at pre-merge revisions; later changes were not re-audited) still rated about 5 of 20 English explanations wrong, mostly by repeating a wrong detector evidence phrase. Llama prose remains English; the Hindi summary is fixed text, labelled as not AI-written.
12. **Can a prompt injection or subtle scam bypass the assistant?** Prompt-injection rules, data-framing prompts, and detector-authoritative verdicts mitigate override attempts (injection holdout FPR 0.154, recall 0.938), but they are heuristic guards, not formal proofs. In our 24-scam adversarial suite, 2 scams still slip through (typically mixing an official app reference with an unofficial WhatsApp/link). `NO RISK FOUND` always adds *"still verify."*
13. **What about language coverage and user testing?** The Android r2 UI supports English and Hindi chrome/steps/evidence, and detectors cover English, Devanagari Hindi, and Hinglish. Other Indic scripts (Marathi, Tamil, Telugu, Bengali, etc.) are not yet covered, and non-expert/elderly user comprehension and TalkBack accessibility have not been formally user-tested.
14. **Does LOCO F1 1.0 prove real-world generalisation?** No. Leave-one-category-out F1 1.0 was measured on 32 project-generated synthetic categories with fixed rules active and `uncertain` mapped to benign; it is a sanity check, not a field estimate.
15. **What are Call Guard and the UPI QR check?** Both merged on 24 Nov. The UPI checker parses `upi://` payloads and QR strings offline and explains the result through the same Llama path. Call Guard (a separate `bin/callguard` CLI; in the web app only with `PRAHARI_CALL_GUARD=1`) transcribes a shared voice note with Arm's INT8 Whisper Tiny through ExecuTorch and checks it for the digital-arrest script; it has only been measured on the Oracle N1 VM on four synthetic English TTS clips (Hindi came out SUSPICIOUS, not STOP), and its Android screen is not wired in.
16. **What about a copied bank alert with a fake link?** Since PR #54 the detector marks a debit or OTP alert that names a lookalike or throwaway domain ("Not you? Visit sbi-refund-help.dev") as SUSPICIOUS rather than NO RISK; genuine alerts that name the bank's own site or app stay clear. The sealed and v4 held-back scores above predate this rule and were not re-run.
